# Oblada

Oblada is a Chromium-based browser for macOS: Zen's design (tabs, address bar and workspaces in a left sidebar, compact mode, split view), Firefox's containers (a storage partition per container, "always open this site in…"), and extensions from both the Chrome Web Store and Firefox Add-ons (`.xpi` converted on install, Firefox's `contextualIdentities` API). The user writes in Italian: reply in Italian.

## Layout

It's a Chromium fork laid out like Brave. Chromium itself is never committed; the checkout lives in `~/chromium` (`$OBLADA_CHROMIUM`), and its sources are in `~/chromium/src`.

| Path | What it is |
| --- | --- |
| `Makefile` | the commands, over the scripts below: `make` lists them (`build`, `patches`, `test`, `screenshot`, `dmg`, `bump`, `release`…). Written for macOS's GNU Make 3.81 |
| `chromium/CHROMIUM_VERSION` | the pinned Chromium release |
| `chromium/oblada/VERSION` | Oblada's own version (0.1.0…), apart from Chromium's: the About page and `oblada://version` show it with the Chromium it's based on, and releases are named and tagged after it. C++ gets it as `OBLADA_VERSION` from the generated `oblada/version.h` |
| `chromium/args.gn` | build args, copied into the build directory by `build.sh` |
| `chromium/oblada/` | Oblada's own code (namespace `oblada`), linked into the checkout as `src/oblada`; sources are listed in `oblada/browser/sources.gni` |
| `chromium/patches/` | Oblada's edits to Chromium's files, one patch per file |
| `chromium/overrides/` | files that replace Chromium's whole (the logo's images and vector icons), copied over them at the same paths |
| `chromium/scripts/` | `sync.sh` (with `deps.py`, which keeps the dependencies one commit deep), `build.sh`, `patches.sh`, `rebrand.py`, `sparkle.sh`, `smoke.mjs`, `updates.mjs`, `screenshot.mjs`, `lib/oblada.mjs`, `dmg.sh`, `appcast.py` and `release.sh` (see Releases) |
| `changelogs/` | public release notes, as Zen's, one JSON file per version (`0_1_1.json`) for the website to read when it's generated; `changelogs/README.md` describes the format: `obladaVersion`, `chromiumVersion`, `releaseDate` (strings: `releaseDate` is `YYYY-MM-DD`, empty until the release) and `released` (bool), `releaseId` (a number, one more for each release: 0.1.0 was 1, 0.1.1 is 2), and optional lists of short sentences for users, `added`, `changed`, `removed`, `fixed`, `knownIssues`, `notes` |
| `devlogs/` | what changed in each version in detail, for contributors, one Markdown file per version (`0_1_1.md`) |
| `TODO.md` | work planned and left for later (official release builds, Linux and Windows releases), with what's known so far: start there when picking one up |
| `branding/` | the logo, an occhiata's tail: `logo.py` draws it, `export.sh` writes every image and vector icon Chromium shows its logo with into `chromium/overrides/`. `vector_icon.py --svg <size>` gives the one-color glyph as an SVG path for the `chrome-product` icon of WebUI iconsets, which are carried as patches. `dmg/` is the DMG window's background: `render.mjs` draws `background.html` into its PNGs |

## Workflow

- Change Chromium files in `~/chromium/src`, then run `chromium/scripts/patches.sh update` to rewrite `chromium/patches/`. Mark Oblada's lines in Chromium files with `// Oblada` comments. Put new code in `chromium/oblada/`, not in Chromium's tree, and list it in `sources.gni`. Keep `PATCHES.md` in step: a new or removed patch, or one that changes purpose or depends on another, gets its entry updated.
- `chromium/scripts/build.sh` applies what isn't applied yet (patches, overrides, and the "Chromium" → "Oblada" renaming of strings in every language by `rebrand.py`), then builds. Don't hand-edit `*chromium_strings*` files.
- Build output is `Oblada.app` in `out/Oblada`, or in the checkout's existing build directory (the scripts find it). Renaming a build directory means a full rebuild of about 6 hours. A typical incremental build takes a few minutes; run long ones in the background.
- User-visible strings for Oblada's own UI live in `oblada/browser/l10n.cc`, in English and Italian. Prefs are named `oblada.*`. Internal pages are shown as `oblada://` (they are `chrome://` underneath).
- Every change goes, as it lands, into the next release's devlog (`devlogs/<x_y_z>.md`: what and how, with files and names) and, if users would notice it, its changelog (`changelogs/<x_y_z>.json`: one plain sentence in `added`, `changed`, `removed`, `fixed`, `knownIssues` or `notes`). Both are in English and kept up to date until the release.
- Commit only when the user asks.

## Releases

Releases are published on GitHub (`Oblada-Browser/oblada`) with `chromium/scripts/release.sh <notes.md>`; the DMG is never committed. Installed apps update themselves from them (`oblada/browser/updater`, Sparkle on macOS, which `sparkle.sh` puts in the checkout as `third_party/sparkle`): a release also has `Oblada-<version>-arm64.aar` (the same app as an Apple Archive, which updates unpack without mounting a disk) and `appcast.xml` (the feed apps read at `releases/latest/download/appcast.xml`, written by `appcast.py`), both signed with the EdDSA key in the maintainer's login keychain (`make update-key`, once, or `make import-update-key FILE=<backup>` from a backup made with `generate_keys -x`; `PUBLIC_KEY` in `oblada/browser/updater` is its public half, and `release.sh` checks they match). Only `dmg.sh` turns the updater on, in the packed app's Info.plist (the feed, the key, `CFBundleVersion` set to Oblada's version): builds never update themselves. `make test-updates` (`updates.mjs`) checks it all end to end, headless, with a key of its own. A release is Oblada's version (`chromium/oblada/VERSION`): tag `0.1.2`, `Oblada-0.1.2-arm64.aar`; its DMG is always `Oblada-silicon.dmg` (0.1.0 and 0.1.1 had versioned names). The file holds the version of the last release until the next one: raise it (0.1.0 → 0.1.1) to release, and `release.sh` refuses a version already released from another commit. Versions follow Semantic Versioning, in its 0.y.z form for initial development: a release with new features or changes users notice raises the minor version (0.1.2 → 0.2.0), one with only fixes (a newer build of the same Chromium among them) the patch version (0.2.0 → 0.2.1). The next version's changelog and devlog are named after it: when a feature lands in a version that only had fixes, rename them (`0_2_1` → `0_3_0`) and their `obladaVersion` and title. The first release, 0.1.0, kept its old tag, `155.0.8059.85-1`: the next one is 0.1.1. The notes get the Chromium version it's built on, and start from the version's changelog (`changelogs/`): on release day, set its `released` to true and its `releaseDate`, and replace the devlog's "Not released yet" line with the date. The release is marked as the latest. The website's download button (`lib/site.ts` in the website's repo) links to `releases/latest/download/Oblada-silicon.dmg`, which always leads to the latest release's DMG. The website reads the changelogs when it's generated, statically: it's updated last, after the release is published and its changelog, marked released, is pushed. `dmg.sh` signs the app ad hoc as a whole (the build is only linker-signed, which macOS calls damaged once downloaded) and lays out the DMG's window with dmgbuild, without opening Finder. Release notes are in English: what Oblada is, crediting Zen, how to install it past Gatekeeper, known limits.

## Testing: never take the user's focus

The user keeps working while tests run. Everything runs headless, driven over the DevTools protocol, with a throwaway profile:

- `node chromium/scripts/smoke.mjs`: about 40 checks, takes a few minutes. Its final check fails if Oblada ever came to the front. `a tab dragged onto the page goes next to it (split view)` is known to be flaky in full runs.
- `node chromium/scripts/updates.mjs` (`make test-updates`): the updater end to end, about 20 checks in some 10 minutes. It packs the build as a release with a key of its own, serves the feed from a local server, updates an older copy installed in a temporary folder, and checks that tampered updates are refused. Its apps have their own bundle id (`….update-test`), so Sparkle's settings and caches are the test's; it removes them at the end.
- `node chromium/scripts/screenshot.mjs out.png [--mode=scaffold|compact] [--media=<n>] [--do="…"]`: the window including the browser UI, plus `out.layout.txt` (every view and its bounds) and `out.popup.png` for an open bubble. `--media` opens tabs playing silent music, for the media controls at the bottom of the sidebar. The window's background (its workspace's theme, `oblada/browser/ui/window_background.h`) is drawn under the views, on a gray standing for the glass, which on screen blurs what's behind the window; `out.layout.txt` says what it is (`window background colors=… opacity=… grain=…`). A `hover:` lasts until the window rechecks the real pointer, so catch hover animations with `film:`. The `--do` actions are documented in `oblada/browser/debug/window_snapshots.cc`: command ids, `click:<view class>`, `hover:<view class>`, `split`, `drag:`/`drop`/`grip:`, `type:`, `press:<x>,<y>`, `select-to:<n>`, `open:<url>`, `temporary` (a tab in a new temporary container), `site-panel`, `force-click` (a peek at the link under the pointer)/`peek-tab` (the peek made a tab), `expand`, `escape`, `wait:<ms>`, `ws-new`/`ws-next`/`ws-prev`/`ws-icon:`/`ws-color:`/`ws-picker`/`ws-container:`, `ws-theme` (the theme picker)/`ws-theme-dots:`/`ws-theme-scheme:`/`ws-theme-opacity:`/`ws-theme-grain:`/`ws-theme-default`, `ws-header` (the workspace's header shown), `mode:` (the window's layout), `default-theme` (its picker)/`default-theme-reset`, `swipe:`/`swipe-timed:`/`swipe-end`, and `film:<count>:<ms>` (frames of an animation).
- `lib/oblada.mjs` launches an APFS clone, `Oblada Test.app`, with its own bundle id, so that clicking Oblada in the Dock never reaches a test instance. It also passes `--use-mock-keychain`, and `--disable-features=MacAppCodeSignClone`: Chromium otherwise clones the app into `/var/folders/…/X` at each launch and removes the clone only when it quits normally, so killed instances leave clones that keep old builds' blocks (they once took ~290 GB). Launch Oblada by hand with it too.
- Never launch the user's real profile (`~/Library/Application Support/Oblada`), never `pkill` Chromium or Oblada broadly (kill only your own PIDs), and ask before anything that needs a visible window.
- Crash dumps are in `~/Library/Application Support/Oblada/Crashpad/pending/` (test runs write there too). The build has no symbols: `strings -n 8 <dmp> | grep -E 'FATAL|Check failed'` gives the failing line. For a crash without one (e.g. a segfault), macOS's report `~/Library/Logs/DiagnosticReports/Oblada-*.ips` (JSON) names the functions on the crashing thread.

## Code style

Follow Chromium's style. Comments are short sentences saying what something is for, written for someone reading the code cold. Don't add comments that only narrate the change.
