# Oblada 0.1.2: devlog

Released on 2026-10-21. Based on Chromium 155.0.8059.85. What changed since 0.1.1, in detail; the
public release notes are in [`changelogs/0_1_2.json`](../changelogs/0_1_2.json).

## Updates

Oblada updates itself from its GitHub releases, with
[Sparkle](https://sparkle-project.org) 2.10 on macOS (`oblada/browser/updater/`).

- **How it goes.** Once a day (and when About Oblada opens) the updater reads the feed of
  the latest release, `releases/latest/download/appcast.xml`. A newer version is
  downloaded in the background and checked, then waits: Sparkle replaces the app once
  Oblada has quit, or right away from About's "Relaunch": Oblada hands it to Sparkle and
  quits as the menu's Quit does (Sparkle would ask it to with a quit event, which a
  headless Oblada never gets; automation's DevTools hold on a headless Oblada is let go
  too), then Sparkle installs it and opens Oblada again.
  Chromium's own relaunch would open the old app while it's being replaced
  (`application_lifetime_desktop.cc`). The next start restores the session, as after
  Chromium's own relaunches, even when "On startup" opens the New Tab page
  (`oblada.updater.restore_session` in Local State, `--restore-last-session`).
- **No windows of Sparkle's.** `ObladaSparkleDriver` (`updater_mac.mm`) is Sparkle's user
  driver and delegate: it accepts what Sparkle would ask, and reports to `updater.cc`,
  whose `VersionUpdater` is the About page's (`about_handler.cc`): checking, the
  download's progress, "Nearly up to date" with Relaunch, up to date, or Sparkle's error.
  A headless Oblada isn't relaunched as a window.
- **Only releases update themselves.** Sparkle.framework is in every build
  (`Contents/Frameworks`, from `chrome/BUILD.gn`), loaded at startup rather than linked,
  so helpers don't load it. But only `dmg.sh` gives the app what turns the updater on, in
  its Info.plist: the feed (`SUFeedURL`), the public key (`SUPublicEDKey`, from
  `oblada/browser/updater/PUBLIC_KEY`), daily checks and automatic downloads, and
  `CFBundleVersion` set to Oblada's version, which Sparkle compares with the feed's (it
  was Chromium's build number, which LaunchServices alone reads). A build from
  `build.sh` never replaces itself with a release, and its About page shows no update
  status.
- **What's downloaded.** Not the DMG: `dmg.sh` writes the same app, signed the same way,
  as an Apple Archive next to it (`Oblada-<version>-arm64.aar`), which Sparkle unpacks with
  `aa` instead of mounting a disk. In the update test, Sparkle mounting the DMG stalled
  once in macOS's disk check (`fsck_hfs`) for over 15 minutes.
- **Signed twice.** The archive and the feed are signed with an EdDSA key whose private
  half is in the maintainer's login keychain (`make update-key`, once; keep a backup, or
  installed apps can't be updated again). `make import-update-key FILE=<backup>` puts a
  backup (`generate_keys -x`) back in the keychain, or on another Mac, and checks it's
  the key `PUBLIC_KEY` holds (or writes `PUBLIC_KEY` when there's none yet). The app refuses an unsigned or changed feed
  (`SURequireSignedFeed`) and checks the archive before unpacking it
  (`SUVerifyUpdateBeforeExtraction`); Sparkle also refuses downgrades. What Sparkle
  downloads isn't quarantined, so updates don't go through Gatekeeper's prompt again.
- **Sparkle in the checkout.** `chromium/scripts/sparkle.sh` (run by `build.sh` and
  `sync.sh`) puts Sparkle's prebuilt release in `src/third_party/sparkle`, pinned by
  version and SHA-256: the framework, and its `sign_update` and `generate_keys` tools. Its
  `README.chromium` lists it in `oblada://credits` (MIT).
- **Releases.** `release.sh` checks that the keychain's key is `PUBLIC_KEY`'s, and
  publishes the archive and `appcast.xml` next to the DMG. `chromium/scripts/appcast.py`
  writes the feed: the version, the archive's URL, size and signature, the version's
  changelog as release notes, and the feed's own signature. It needs the version's
  changelog.
- **The update test.** `make test-updates` (`chromium/scripts/updates.mjs`) packs the build
  as a release with a key made for the test, serves the feed and the archive locally, and
  updates an older copy (out of the DMG), headless: found at startup and installed on
  quit (the signature holds, nothing quarantined), or checked from About and installed by
  Relaunch with the session restored. It must refuse an update signed with another key or
  changed after signing, a feed changed or signed with another key, and a downgrade; a
  missing feed is an error and nothing more. A build's About page shows no update status.
  The apps are copies with their own bundle id, so Sparkle's settings and caches are the
  test's.
  `lib/oblada.mjs` can launch an app as it is (`copy: false`).
- About's update status, which 0.1.1 hid, is back (`about_handler.cc`).

## Releases

- The DMG is always `Oblada-silicon.dmg` (for Apple silicon Macs), whatever the version
  (`dmg.sh`): the website's download button links to
  `releases/latest/download/Oblada-silicon.dmg` and follows each new release without
  changes. 0.1.0 and 0.1.1 had versioned names (`Oblada-0.1.1-arm64.dmg`). The update
  archive keeps its version (`Oblada-0.1.2-arm64.aar`); `dmg.sh` prints its path, then
  the DMG's.

## Keychain

- Oblada's key for saved passwords and cookies is now "Oblada Safe Storage" (account
  "Oblada") in the Keychain, not Chromium's "Chromium Safe Storage"
  (`keychain_password_mac.mm`). Other Chromium-based browsers use Chromium's names: on a
  Mac with one of them, Oblada's first launch found its key and macOS asked for the user's
  password to let Oblada read it. There's no migration: Oblada had no other users, and
  the maintainer's key was copied to the new name by hand (`security`). A profile from
  0.1.1 or earlier gets a new key, and loses what it had saved encrypted (logins,
  passwords).
- macOS still asks after each update: the app is signed ad hoc, so each version is a new
  app to the Keychain until "Always Allow". Only a Developer ID signature, the same for
  every version, avoids it.
- Importing passwords from a Chromium-based browser on macOS reads that browser's key, and
  macOS asks for the user's password: the welcome page now says so before
  (`welcome.import_keychain`; the import handler tells the page which sources ask,
  `asksKeychain`).
