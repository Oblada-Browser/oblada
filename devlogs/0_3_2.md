# Oblada 0.3.2: devlog

Not released yet. Based on Chromium 156.0.8078.48. What changed since 0.3.1, in detail; the
public release notes are in [`changelogs/0_3_2.json`](../changelogs/0_3_2.json).

## Releases are official builds

Chromium wants `is_official_build = true` for any build that ships to users
(`build/config/BUILDCONFIG.gn`); Oblada's releases were plain release builds, as the
development build is. They're now built apart, in `out/Release`, with
`chromium/args.release.gn` added to `args.gn`, as Chrome, Brave and Helium are:

- **PGO** (`chrome_pgo_phase = 2`, `build/config/compiler/pgo/pgo.gni`) with Google's profile
  for the pinned Chromium, which `chrome/build/mac-arm.pgo.txt` names (85 MB to download,
  315 MB unpacked in `chrome/build/pgo_profiles/`). `sync.sh` now writes
  `"checkout_pgo_profiles": True` in `.gclient`, so `gclient runhooks` fetches it, with V8's
  profiles for its builtins (`v8/tools/builtins-pgo/profiles/`), which official builds use too
  (`v8_enable_builtins_optimization`). Oblada's patches don't stop the profile from applying:
  the functions they change lose theirs, and `build/config/compiler/pgo/BUILD.gn` already
  silences the warnings about it.
- **ThinLTO with optimizations** (`use_thin_lto`, `thin_lto_enable_optimizations`). Its cache,
  `out/Release/thinlto-cache`, speeds up the next builds' links; Chromium keeps it under the
  lesser of 10% of the disk's free space and 40 GB (`build/config/compiler/BUILD.gn`).
- **Stripped binaries**, with dSYMs made as they're linked (`enable_stripping`,
  `enable_dsyms`, `build/config/apple/symbols.gni`). `symbol_level` stays 0: the dSYMs hold the
  symbol table, the functions' names, without debug info, so `dsymutil` takes seconds and the
  app's dSYMs take some 25 MB compressed.
- CHECK failures lose their message, file and line (`CHECK_WILL_STREAM()` in `base/check.h`).

### Measured

On the M4 (24 GB), against the development build of the same sources (as releases were
built until 0.3.1):

- **Speedometer 3.1**: 57.3 against 40.2, **+42%**. Headless, with a throwaway profile, three
  runs of 10 iterations for each build, taken in turns: 55.9, 57.9 and 58.2 against 40.0, 41.0
  and 39.7.
- **Size**: the app takes 351 MB against 551 MB. Most of it is the framework's symbol table
  (178 MB), now in the dSYMs, but its code is smaller too: the framework's `__TEXT` is 235 MB
  against 253 MB. The DMG is 165 MB, against 189 MB for 0.3.1's, and the update archive 164 MB
  against 188 MB.
- **Building**: the first build took 4 h 16 min; `out/Release` takes 11 GB, 1.3 GB of which is
  the ThinLTO cache. With it, building again after changing one of Oblada's files took 89 s,
  link included.

Not taken: what Thorium adds on top of an official build (-O3 everywhere, AVX2/AVX-512
builds, `-ffp-contract=fast`, lower libc++ hardening, LLVM's GVN hoist and Polly). Its gains
over Chrome aren't shown by independent measurements, and the developer behind most of these
flags calls -O3's gain trivial
([RobRich999/Chromium_Clang#26](https://github.com/RobRich999/Chromium_Clang/issues/26#issuecomment-951919715)).
`-mcpu=apple-m1` is already clang's default for arm64 macOS.

### Building and releasing

- `build.sh --release [targets]` (`make build RELEASE=1`) builds `out/Release`, writing its
  `args.gn` from `chromium/args.gn` and `chromium/args.release.gn`. `env.sh` names it
  `RELEASE_OUT` and never takes it for the development build, nor does `lib/oblada.mjs`.
  `make run RELEASE=1` and `make run-fresh RELEASE=1` open it.
- `release.sh` builds and packs it (`dmg.sh --release`, `make dmg RELEASE=1`). It then keeps
  the dSYMs of the app's binaries, matched by UUID (those of the build's own tools are there
  too), in `~/chromium/symbols/Oblada-<version>-arm64-dSYMs.aar`, on the maintainer's Mac:
  they're never published.
- `symbolicate.py` (`make symbolicate IPS=<report.ips>`) names Oblada's functions in macOS's
  crash report of a release: it reads the report's Oblada version (`build_version`, which
  `dmg.sh` sets), unpacks that release's dSYMs into the temporary directory once, and prints
  the crashed thread (`--all`: every thread) with `atos`'s names, the system's frames as the
  report names them. Functions the linker folded into one, having the same code (lld's ICF),
  show as `<deduplicated_symbol>`.

### Patches

Comments only, no change in behavior: `base-check.cc.patch`,
`content-browser-webui-web_ui_main_frame_observer.cc.patch` and
`components-webui-version-resources-about_version.html.patch` said Oblada wasn't an official
build. The first two now only change development builds, as official ones already behave so;
the version page still hides its build label, now "(Official Build)" in releases.

## A crash after restoring a session

Restoring a session saved each workspace as a tab group: `ProcessSavedGroup()` in
`chrome/browser/sessions/session_restore.cc` saves any restored group not saved yet, with the
tabs restored so far, and connects it to the copy once the tab group service has loaded. A tab
opened in the workspace in between (a link opening Oblada, or any tab opened right after
launch) made the `tab_group_sync_delegate_desktop.cc` patch leave the group unconnected rather
than close tabs to match the copy. But the copy kept the workspace's id, so the new tab's next
navigation failed `CHECK(tab)` in `SavedTabGroupWebContentsListener::DidFinishNavigation()`
and crashed the browser.

The smoke test hit it once, opening `oblada://discards` right after its restart. A script that
restores a session, opens a tab at once and navigates it a few seconds later crashed every
time, 7 out of 7, on both builds. `ProcessSavedGroup()` now returns early: restored workspaces
are neither saved nor connected, as new ones already weren't. The same script no longer
crashes (10 out of 10, on both builds), nor on a profile whose workspaces 0.3.1's code had
already saved (3 out of 3): those copies are never connected again.

## Tests

- The smoke test runs on the release build too: `node chromium/scripts/smoke.mjs <Oblada.app>`,
  `make test RELEASE=1`. On it: 64 out of 64, in each of five runs; `updates.mjs` on it: 23
  out of 23.
- `the welcome offers the three layouts, and picking one sets it` failed now and then on the
  development build: the layouts show before `welcome.js`, a module, listens to them, so on a
  slow first launch the click came too early. It now clicks until the layout takes.
